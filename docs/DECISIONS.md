# Decision log

The fixed decisions F1–F12 are in `BUILD_SPEC.md` §0 and are not repeated here. This file records the
implementation decisions taken while building v1.4.1. Each one resolves a gap or ambiguity in the spec and was
reported to the founder before being applied. **None of them weakens an invariant** (I1–I7, C1, S1–S4).

| # | Spec § | Issue | Decision |
|---|---|---|---|
| D1 | §5.4, §7.5 | `ChainConfig` has no `maxTotalOutstanding`, but the constructor needs it and caps must come only from the registry | Added `maxTotalOutstanding: bigint` to `ChainConfig` (mainnets 1,000,000,000; testnets 0) |
| D2 | §7.5 | `Deploy.s.sol` cannot import the TS registry | `pnpm --filter @flying-money/chains gen` writes `packages/chains/registry/<key>.json` from the TS registry; the script reads it with `vm.parseJson`. A test fails if the files are stale. `anvil` USDC is registered at runtime (`setLocalDeployment`) after MockUSDC is deployed |
| D3 | §6.5 steps 3–4, §6.6 step 2 | A retry of an already-SERVED request near expiry would get 402 without a receipt, and the client would resend forever. The client had no rule for a deterministic rejection | (i) Server: for a `requestId` that already has an outcome, return the stored outcome **before** the step-3 lifetime/closed check (no admission happens, so no new charge). The ECDSA check runs before a stored response is returned, so a forged note with a copied memo can't read it. (ii) Client: a rejection **without a receipt** (400/401/402) means the note was never admitted, so `pending` is cleared with no state change. C1 holds because no obligation grew |
| D4 | §6.4 vs §8.1 | Integers are "decimal strings", but the examples show `expiresAt`, `v` and `minRemainingLifetime` as JSON numbers | `v` and `minRemainingLifetime` are JSON numbers. Every other integer (`chainId`, amounts, `expiresAt`) is a decimal string |
| D5 | §6.5 step 5 | First sight of a new certificate is indistinguishable from a lost store | Initialise as `accepted = consumed = redeemedOnChain`, `reserved = 0`. Status is `RECOVERED` only when `redeemedOnChain > 0`, otherwise `OK`. Admission maths is identical either way |
| D6 | §8.3 | The redeemer's `maxAgeSeconds` rule needs a timestamp the store interface doesn't expose | `pendingRedemptions` items carry an optional `oldestServedAt` (ms) |
| D7 | §6.5 | "`redeemedOnChain ≤ accepted` MUST hold" can be broken by the spender redeeming directly on-chain, which §6.5 allows | Asserted in property tests where only the seller redeems. Outside that, the seller is paid more, never less |
| D8 | §7.2 vs §0.2 | The reference code was verified on `paris`; the pin is `shanghai` | `evm_version = "shanghai"` (the pin wins) |
| D9 | §0.2 | Foundry 1.x removed `forge install --no-commit` | Same installs without the flag, as git submodules pinned to tags (forge-std v1.10.0, OpenZeppelin v5.1.0) |
| D10 | §6.7, §7.1 #7 | The contract's 1 h minimum lifetime equals the server's `minRemainingLifetime`, so a 1 h certificate is refused almost immediately | Demo certificates use lifetimes ≥ 1 day. The testnet smoke test's reclaim step waits > 1 h |
| D11 | §5.3, §8.3 | Store backend: the founder has no Redis and doesn't want Docker; the web deploys to Vercel | **Upstash Redis** (Vercel Marketplace, HTTPS, supports Lua `EVAL`, durable). One Lua-script store with two transports: `upstashStore()` (HTTP, Vercel) and `redisStore(url)` (TCP, any Redis). The S4 Redis tests run in GitHub CI against a Redis service container, and locally when `UPSTASH_REDIS_REST_URL`/`TOKEN` or `REDIS_URL` is set |
| D12 | §0.2 | TypeScript version | TypeScript 7.0 (latest stable at build time) |
| D13 | §6.8 | The spec estimates a sealed-note QR at "about 350 characters"; the normative encoding (`fm1.` + base64url(JSON)) gives about 544 | No format change. 544 bytes still fits **one** QR at error-correction level M (version 18-M holds 593 bytes), so the §6.8 claim holds. A test asserts ≤ 593 |
| D14 | §8.3 | Additive, optional fields and knobs the spec leaves open | `Submission.nonce` (lets the redeemer detect a dropped or replaced tx without rebroadcasting); a `Flying-Money-Reason` response header on 402s (`insufficient`, `wrong-payee`, `expiring`…) so the client knows when to refresh (§8.2); `pollingIntervalMs` on the redeemer. The wire JSON of offers, notes and receipts is unchanged |
| D15 | §6.5 step 10 | Sweeper behaviour when the app gives no `requestStatus` | Stale PENDING resolves as **failed → credit** (buyer-safe; the seller carries the risk). Sellers with side effects should provide `requestStatus` (the `createIdempotency()` helper does) |
| D16 | §7.5, H4 | Explorer API keys are optional: the founder prefers keyless verification | `pnpm deploy:chain <key> --verify` verifies on **Sourcify** (keyless, full source match, shown by Blockscout and sourcify.dev) when `EXPLORER_API_KEYS` is unset. Etherscan-family verification (Arbiscan/Basescan badge) runs when a key is added later, and can be re-run on an existing deployment with `forge verify-contract` |
| D17 | §13.3, §5.3 | Where the /demo runner and its Oracle run for Sprint A | The runner is a Next.js route (`/api/demo/run`, Node runtime, `maxDuration` 300) holding the testnet demo keys server-side (§13.3). It issues a fresh 0.30 USDC certificate per run and runs the Oracle **inside the runner**; the agent calls the Oracle's fetch handler directly (same 402 / note / receipt flow, no socket), because a localhost server inside a Next request handler hung. Runs are serialised (the funder's nonce), 1 per IP per 2 min, with a 4-minute timeout that releases the lock. Every transaction is real. A standalone, durable Oracle (Upstash) for external agents comes with the MCP work in Sprint B |
| D18 | §5.3, §12.1 | ConnectKit supports only React 18 / wagmi 2 and RainbowKit needs wagmi 2 plus a WalletConnect project id; the web app runs React 19 | **wagmi 3** with the injected (browser-wallet) connector and a Counting House connect button in the site's style. WalletConnect for mobile wallets can be added later with a project id (a human input) |
| D19 | §17 Sprint B (Playwright issue→redeem on anvil) | A browser e2e needs a wallet without handling any real key | A local-only **e2e mode** (`NEXT_PUBLIC_FM_E2E_*`, set by `pnpm --filter @flying-money/web e2e:anvil setup` into the git-ignored `.env.development.local`): the Counting House points at a private anvil and uses wagmi's `mock` connector, whose transactions anvil signs with its public, unlocked dev accounts. Never enabled in production builds |
| D20 | §6.6, §6.8 step 2 | At a counter there is no receipt channel from the till back to the phone, so the wallet cannot see the "final state" §6.6 step 6 waits for | The customer supplies it after reading the till's screen: **Done** (the till showed Accepted → `consumed += price`, `accepted = the note's total`) or **The shop didn't accept it** (clears the open order, like a rejection without a receipt, D3). Until one is chosen the wallet re-shows the same QR and refuses other orders. Neither choice lets the wallet sign more than it already signed plus one new order's price (C1, randomised test with crashes). The sealed note itself is unchanged |
| D21 | §6.5, §6.8, §12.5 | Where the till keeps its authoritative seller state in a browser | The same `memoryStore` (§6.5 logic unchanged) with an `onCommit` hook that saves a full snapshot in one atomic IndexedDB write before any `begin`/`finish` result is shown. The S1–S4 store and server tests also run against a store re-opened from its saved snapshot on every call. Certificates the till has read on-chain are cached durably; that cache is what "verified by this shop earlier" means for GUARANTEED. UNVERIFIED value is capped **per certificate** by the first-visit limit, is never written into the guaranteed ledger, and is re-run through §6.5 on reconnect (promoted or flagged). A sealed note whose memo is not keccak256(current order id) is rejected, so an old QR can't pay for a new order |
| D22 | §13.3 | The /demo scenario buttons assume a long-lived runner, but the runner is one streamed request on Vercel serverless, so a second request can't reach the run in flight | **Cut the network** and **Steal the agent key** are toggles chosen before pressing Run, and the run performs them live at scripted moments. The seller's certificate reads fail for part of the run (notes keep being accepted from its cache; redemption waits; one transaction collects after the restore). Then a thief holding the agent key tries three things: overspend at the seller (402 insufficient), redeem that note on-chain (a read-only call that reverts `ExceedsFaceValue`, no gas), and pay a different seller (402 wrong-payee). **Redeem now** runs at the end of every run, and **Reset** is simply a new run: each run issues a fresh certificate. Every outcome is a real check. An anvil test asserts all of it in CI |
| D23 | §21.1 | How the local gate works without hosted CI | `pnpm verify` (`tools/verify/verify.ts`) runs, in order: biome; a clean site build (everything in `apps/web/.next` except `cache/` is deleted, so the denylist never sees stale chunks and fonts aren't re-downloaded); typecheck including `tools/doc-samples`; `pnpm test` (turbo: C1, S1–S4, the counter tests, forge unit + invariants, the agent e2e on anvil); the secret scan; the public-surface check. `--e2e` adds Playwright. Only the store variables (`KV_REST_API_*`, `UPSTASH_REDIS_REST_*`, `REDIS_URL`) are passed from `.env` to the tests, never keys. S4 on Upstash uses a `fm:test:<random>:` prefix that is deleted after the run. **Secret scan:** gitleaks is used when installed; otherwise the bundled scanner reads `git ls-files -co --exclude-standard` and flags three things: private-key assignments, token patterns (Anthropic, OpenAI, GitHub, AWS, Slack, Google, Upstash, Vercel, `CRON_SECRET`), and the literal value of any secret-looking `.env` entry appearing in a file. It never prints values; a planted key was caught in testing. **Git:** local commits per phase; nothing is pushed until the founder says so (the Vercel project deploys from GitHub pushes, so no deploys until then either) |
| D24 | §21.2 | Chain pages, preselection and the denylist check | `/chains/[chain]` is static for every registry key except `anvil`. It shows name, status, contract (explorer + verified-source link: Blockscout when the registry has `blockscoutApi`, else the explorer's code tab), USDC, gas token, caps, faucet, and the registry's new **`notes`** field. The §5.4 `hackathons` field is removed from the registry because the registry ships in browser bundles, so it counts as a public surface. "Try it" buttons use `?chain=`. `usePreferredChain` validates the key against the allowed list and remembers it in localStorage; it is used by the Counting House, Open a shop and `/demo`. `/shops` forwards `?chain=` to its links. The demo route accepts a deployed testnet from the body, else the default. Event material lives in `docs/submissions/<event>.md` (not served: the docs site reads only `docs/site/`). **Denylist check:** `tools/public-surface/denylist.txt`, case-insensitive, over every served file type in `.next/server`, `.next/static` (source maps excluded), `apps/web/public` and `docs/site` |
| D31 | §21.3, §11 | The §21.3 words were still too abstract for first-time readers ("sealed certificate", "sealed note") | User-facing copy follows `docs/copy/copy-deck.md`: the tagline is "Hand over a budget, not your wallet."; a signed note is called a **payment slip** in the UI (docs keep "signed note" and name the UI term once); the Counting House is labelled **Dashboard** in navigation, with tabs **Give & collect · Holders · Places**. Protocol, contract, SDK identifiers and wire formats are unchanged. The landing page offers two doors (**For AI agents** / **For families & shops**) whose variants share one grid cell, so switching never changes layout height; the choice is kept in localStorage `fm-door`. On phones, text fields may shrink below their default width so no page scrolls sideways at 375 px |
| D32 | §6.5 step 4, §8.3; audit F1 | A requestId was bound only to `(certKey, memo)`, so the same signed note replayed on a different route or query re-ran the handler while PENDING ("resume") or when a SERVED response was too large to store. That is service without a new charge (S1/S2) | `begin` takes an optional `requestHash` and stores it in the outcome record, in the same atomic transaction (memory store and Redis Lua). On every replay path (stored outcome, or `DUPLICATE` from `begin`) the server compares it after the ECDSA check (D3). A different or missing hash returns **409** `memo-reused` (`Flying-Money-Reason` header), and the handler never runs. The Hono middleware always sends `requestHash = keccak256(METHOD 
 path 
 sorted query 
 keccak256(body))`, leaving the host out. Resuming or replaying the *same* request is unchanged (§6.5 step 4). The addition to the NoteStore interface is optional, so a store that ignores it behaves exactly as before. Tests: server (all stores), store contract, Hono (the audit's replay farm), and a random replay property |
| D33 | §6.6 step 6; audit F2 | The client updated its state from receipt numbers as given, so a lying seller or a man in the middle could claim `accepted = faceValue` and get the next note signed for the whole budget, bypassing `maxPricePerRequest` | A receipt is trusted only up to what the client signed: `accepted ≤ max(local accepted, pending cumulative)`, `consumed ≤ accepted`, `consumed + reserved ≤ accepted`. Honest receipts always satisfy these bounds, so §6.6 is unchanged for them. A clamped receipt emits `suspicious-receipt`. A receipt for another certificate is refused like a requestId mismatch: pending stays and is resent, never re-signed (C1). Each note is then at most the highest earlier note plus one price (property test with random forged receipts). **Not adopted:** requiring https. With the clamp, a man in the middle can't raise obligations beyond one price, and forcing https would break in-process sellers (`http://oracle.internal`) |
| D34 | §6.8, §12.5 step 4; audit F3 | The per-device offline float in §6.8/§12.5 was not built. Offline, UNVERIFIED value was capped only per certificate, and certificate ids can be made up, so the loss had no bound | `createCounter` takes a required `offlineFloat`: the open UNVERIFIED total across all certificates never exceeds it (`over-offline-float` otherwise), and the result reports `floatLeft`. PROMOTED and FLAGGED records no longer count. The till setting defaults to **20 USDC** (four first-time customers at the default 5 USDC first-visit limit) and is editable in Settings. The UNVERIFIED screen now states the real risk (this payment) and the float left |
| D25 | §21.5 key schema | Details the §21.5 table leaves open | Seller keys are `{p}s:{payee}:{chainId}:{certId}:state` (hash), `…:notes`, `…:out:{requestId}` (hash, `EXPIRE` 30 days in the same atomic `finish`), and `{p}s:{payee}:{chainId}:sub` (hash, field `json`). There are two index keys the table doesn't list, needed to find work: `{p}s:{payee}:{chainId}:certs` (set, for the redeemer) and `{p}s:{payee}:pending` (zset by admittedAt, for the sweeper). **Notes are ordered lexically on a 78-digit zero-padded cumulative (score 0), not by numeric score**: a Redis score is a double and would misorder cumulatives above 2^53, while lexical order is exact. It gives the same order the table intends. **No migration:** the `flying-money-testnet` database was created empty on 25 Sep, and only tests (`fm:test:*`, deleted after each run) used the old layout |
| D26 | §21.5 env, §0.1 | How a process picks its store and refuses unsafe setups | `sellerStoreFromEnv`: `KV_REST_API_*` → `UPSTASH_REDIS_REST_*` → `REDIS_URL` → memory; the prefix is `FM_REDIS_PREFIX` or `fm:v1:${FM_ENV}:`. It throws `DurableStoreRequiredError` when `requireDurable` is set (hosted seller, relay) or FM_ENV is mainnet. A process accepting any mainnet chain needs `FM_ENV=mainnet` and a prefix containing `mainnet`, and must not also accept testnets. `redisFromEnv` gives the same connection to non-seller users (demo limits). Locks use `SET NX PX` (≤ 5 min) with compare-and-delete release; rate limits and amount budgets are Lua counters (decimal-string arithmetic, never floats) |
| D27 | §21.6; audit F8 | The hosted Oracle on Vercel Hobby, and several instances sharing one store | `apps/oracle` gets `api/index.ts` (Node, Web handlers), with `vercel.json` rewriting every path to it, `maxDuration` 60 and a daily cron `0 3 * * *` → `/api/cron/redeem` (Bearer `CRON_SECRET`, compared as SHA-256 digests in constant time; 503 when unset). On Hobby: `safetyBeforeExpiry` = **36 h** and seller `minRemainingLifetime` = **36 h** (a note served at the last moment is redeemed by the next daily run, ≤ 25 h later, before expiry). Policy: 0.10 USDC or 1 h of age. `FM_VERCEL_PLAN=pro` switches to 2 h, meant for a 10-minute cron. After any paid response, `waitUntil(afterServe())` sweeps and redeems, at most once per instance per 30 s. **F8:** the redeemer takes `{p}lock:redeemer:{chainId}` around check-then-submit, so two instances can't both send a batch (anvil test with a delayed store). Startup failures (no durable store, no payee) answer 503 with the reason and never serve on memory |
| D28 | §13.3; audit F9 | The demo's limits lived in per-instance memory: parallel serverless instances could each run the demo, race the funder's nonce and drain the testnet funder | `admitDemoRun`, shared through Upstash: same-origin POST only; the `{p}lock:demo` lock (one run at a time across instances, 270 s TTL, longer than the run timeout); one run per visitor (`x-real-ip`) per 2 minutes; a **daily cap of 6 USDC** locked (20 runs at 0.30, `{p}rl:demo-usdc:{UTC day}`). A busy lock doesn't use up the visitor's slot. On Vercel without store variables the demo answers 503 and never falls back to memory |
